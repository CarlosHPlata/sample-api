# Inventory API

## Description

A small HTTP service that keeps the products of an inventory. It does four things: **create, update, delete and list products**. A product is:

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | generated by the service |
| `name` | string | required, 1–120 characters |
| `description` | string | required, up to 1000 characters, may be empty |
| `price` | number | required, `>= 0`, at most two decimals |

| Method | Path | Does | Answers |
|---|---|---|---|
| `GET` | `/products` | list every product | `200` |
| `GET` | `/products/:id` | get one product | `200` · `400` id is not a UUID · `404` |
| `POST` | `/products` | create a product | `201` · `400` validation |
| `PATCH` | `/products/:id` | update: send only the fields that change | `200` · `400` · `404` |
| `DELETE` | `/products/:id` | delete a product | `204` · `400` · `404` |
| `GET` | `/health` | liveness probe | `200` `{"status":"ok","uptime":12}` |

Requests with unknown fields are rejected (`400`), not silently trimmed.

> **Products live in memory.** Restarting the service empties the inventory. That is deliberate for now, see *Architecture*.

## Technology and internal architecture

| | |
|---|---|
| Runtime | Node.js 24 (`.nvmrc`) |
| Framework | NestJS 12 on Express, TypeScript 6 |
| Validation | `class-validator` DTOs behind a global `ValidationPipe` |
| API contract | OpenAPI 3, generated from the code by `@nestjs/swagger` |
| Tests | Jest 30 + `ts-jest`, `supertest` for the HTTP tests |
| Packaging | multi-stage `Dockerfile`, `docker-compose.yml` for development |

```
src/
├── main.ts                     starts the HTTP server, mounts Swagger UI at /docs
├── app.module.ts               wires the two feature modules
├── app.config.ts               HTTP behaviour shared by the server and the tests (validation)
├── openapi.ts                  the one place that builds the OpenAPI document
├── health/                     GET /health
└── products/
    ├── products.controller.ts      HTTP in, HTTP out. No rules here
    ├── products.service.ts         the rules: ids, not-found, partial update
    ├── products.repository.ts      PORT: what the service needs from a store
    ├── in-memory-products.repository.ts   ADAPTER: a Map in process memory
    ├── product.entity.ts           the Product shape
    └── dto/                        request bodies and their validation rules
scripts/generate-openapi.ts     writes openapi.yml from the code
test/                           tests that boot the whole app in-process
openapi.yml                     the API contract, committed
```

A request flows **controller → service → repository**. The service depends on `ProductsRepository`, an abstract class that says *what* a product store must do and nothing about *how*. `InMemoryProductsRepository` is the only implementation today, chosen in one line of `products.module.ts`. Moving to a real database means writing a second adapter and changing that line; the controller, the service and their tests do not move.

### The API contract

`openapi.yml` at the repo root is the contract other teams integrate against. It is **generated from the code, never edited by hand**:

```bash
npm run openapi:generate
```

Run it after any change to an endpoint or a DTO and commit the result. A test (`test/openapi-contract.spec.ts`) fails when the committed file and the code disagree, so a contract change cannot land unannounced. With the service running, the same contract is browsable at `/docs` (raw: `/docs-yaml`, `/docs-json`).

## How to run it locally

**With Docker** (nothing else to install). Hot reload: edit a file under `src/` and the server restarts.

```bash
docker compose up --build
```

Then open <http://localhost:3000/docs>. If port 3000 is taken: `HOST_PORT=3100 docker compose up --build`.

**With Node 24** (`nvm use` picks the version from `.nvmrc`):

```bash
npm ci
npm run start:dev
```

**The production image**, exactly as it would ship:

```bash
docker build -t inventory-api .
docker run --rm -p 3000:3000 inventory-api
```

It runs as a non-root user and carries a `HEALTHCHECK` that polls `/health`.

Try it:

```bash
curl -s localhost:3000/health
curl -s -X POST localhost:3000/products -H 'content-type: application/json' \
     -d '{"name":"Mechanical keyboard","description":"Tenkeyless","price":89.9}'
curl -s localhost:3000/products
```

| Variable | Default | |
|---|---|---|
| `PORT` | `3000` | port the server listens on |
| `APP_VERSION` | `0.0.0` | written into the contract as `info.version` |

## How to run the tests locally

```bash
npm ci          # once
npm test        # everything
npm run test:watch
npm run test:cov
```

Inside the dev container instead: `docker compose exec api npm test`.

Every test runs in-process: no database, no network, no Docker needed. There are three kinds:

| Where | What it proves |
|---|---|
| `src/**/*.spec.ts` | one class at a time: service rules, repository, controller wiring, DTO validation |
| `test/products.e2e.spec.ts` | the real HTTP surface: status codes, validation, a product's full lifecycle |
| `test/openapi-contract.spec.ts` | `openapi.yml` still matches the code |

Tests need Node **24.9 or newer**: NestJS 12 is published as ES modules and Jest loads it through Node's `require(esm)` support.
